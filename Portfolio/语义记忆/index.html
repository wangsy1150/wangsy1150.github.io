等一个问题…
左边只看字面重叠，右边会先做同义词归一化再加权。同一个问题，两边结果通常不一样。

我做的部分：中文按两字一组切词 → 用 TF-IDF 给每个词算权重（越少见的词越重）→ 句子变成向量 → 用余弦夹角比相似度。你在上面看到的排序，是这段代码当场算的， 不是写死的几组答案。 数据存在浏览器 localStorage 里，关掉再开还在。

我为什么放弃了关键词搜索

我第一版就是关键词搜索

记忆存成纯文本，提问时找共同的字。第一条记忆我写的是「文字堆得再多也没人读」， 转头问「讨厌啰嗦」——一个字都不重合，直接零分。

虚词把我的排序搞乱了

「我今天把那个东西改了」比「变量命名」长得多。按字面重合算，长句更容易赢， 可它其实什么都没说——排在第一位的往往是废话说得最多的那条。

加权之后才分得出主次

换成 TF-IDF，让「变量命名」这种稀有词权重高，「我、的、把、了」趋近零。 同一批记忆，排名立刻变了——真正的主题这才浮上来。

我是怎么算这条的

  • 先切词。中文没有空格没法按词分，所以我按两字一组滑窗切： 变量命名 → 变量 量命 命名。
  • 再算权重。tf × idf：这个词在这句里出现几次 × 它在多少条记忆里出现过（越少越重）。这一步是整套东西的关键。
  • 然后归一化。每条记忆变成一串数字，再除以自身长度—— 不除的话长句天然占便宜，短句永远排不上来。
  • 比余弦。我的提问变成向量，跟每条记忆算夹角余弦，0 到 1，越大越像。
  • 最后排序。取前 3 条，低于 0.05 的直接不显示—— 宁可不给，也别塞几条不相关的。

关键代码

// 核心就三件事：切词、加权、比余弦 function tokenize(text) { const s = text.toLowerCase().replace(/[^\u4e00-\u9fa5a-z0-9]+/g, ' '); const out = []; (s.match(/[\u4e00-\u9fa5]+/g) || []).forEach(seg => { for (let i = 0; i < seg.length - 1; i++) out.push(seg.slice(i, i + 2)); }); (s.match(/[a-z0-9]+/g) || []).forEach(w => out.push(w)); return out; } // 余弦：只看向量夹角，所以长记忆不会天然占便宜 function cosine(a, b) { let dot = 0; Object.keys(a.vec).forEach(t => { if (b.vec[t]) dot += a.vec[t] * b.vec[t]; }); return dot / (a.norm * b.norm); }

这一页里的检索就是上面这段跑出来的，改一个字结果就变。

我知道这个实现的上限在哪。这一页跑的是 TF-IDF 向量 + 余弦 + 一张我自己写的同义词表，纯前端，没有神经网络。它能处理「说法不同但用词相关」， 处理不了真正的同义改写——比如「饭做得难吃」和「厨艺不行」， 我的词表救不了它，那得靠 embedding 模型。这是能力边界，我不想含糊过去。

为什么按项目分组

  • 这是我自己踩出来的。我在做作品集时存了一条「代码块要用深色」， 后来写爬虫时也被翻出来当依据——那时候根本不该听这条。
  • 分组就是命名空间。每条记忆带一个 ns 标记， 默认只在本组里找。
  • 需要时能跨组。勾上「跨项目检索」才全库扫—— 这也是向量库里 where={"ns": "..."} 在做的事。
