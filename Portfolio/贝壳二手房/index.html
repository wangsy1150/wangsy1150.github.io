三个真故障（都能复现）

1

图片列取的是占位图：30 个网址，同一个 1×1 像素

源码里这一行：li.ele('xpath:.//img[@class="lj-lazy"]').attr('src')。 实测 30 条全部返回同一个地址 …/common/blank.gif —— 下载下来是 42 字节、1×1 像素的透明图。真图地址其实在 data-original 属性里。

原因不是「滚得太快」，是取错了属性：懒加载的机制是先给 src 一个占位， 等图片滚进视口、由页面脚本把真地址写进 src。脚本没跑或没跑完，src 永远是占位。

后果是连锁的：后面 add_images_to_excel 会把同一张 1×1 图下载 30 次， Excel 的 H 列看起来塞满了，实际是 30 个白点。

实测 30/30 条 src = blank.gif
2

列表写在循环里：7 页 210 条，最后只剩 30 条

all_data = [] 被写在了 for i in range(1,8) 的内部， 每翻一页就清空一次。所以前面 6 页抓到的数据在下一页开始时就没了，最后一页覆盖全场。

按这段结构复现：循环结束时 len(all_data) == 30，第一条是第 7 页的第一条。 也就是说 180 条被丢掉了，而程序一句错都不报 —— 它看起来是「跑成功了」。

复现：7×30 → 30
3

翻到第 2 页就撞人机验证，第 1 页却是好的

实测状态码：pg1 → 200（228 KB，30 条房源）；pg2～pg7 → 302，全部跳到 hip.ke.com/captcha。

所以验证码不是「随时会出现」，而是卡在翻页这个动作上。这一点源码里的顺序是对的： crack_captcha(page) 就写在 page.get() 之后、取字段之前，每页过一次。

执行流程

  • 翻页请求 — 按 /ershoufang/pg{i}/ 循环取页，每页之间留间隔，不并发。
  • 验证码分流 — 每页进正文前过一次 crack_captcha(page)，按验证类型选择解法： 图形点选走「按图片顺序点击」，滑块走拖拽轨迹，主流程只负责调用和重试。
  • 滚动加载 — 每次下滚 500px 并留 0.3s 给图片加载，比较滚动前后的纵向位置， 位置不再变化才 break。这次实测页面高 8777px、视口 923px，约 16 次到底。
  • 相对路径取字段 — 定位 ul.sellListContent 下所有房源 li， 逐条用 .// 往下找 8 个字段。
  • 落表并插图 — pandas.DataFrame 写出 Excel，再调 add_images_to_excel 把图片嵌进单元格，同时调列宽行高，否则图会盖住邻居。

关键代码

# 滚动到底判断 + 相对路径取字段（源码原样，两处标红的后面再说） from DrissionPage import ChromiumPage import pandas from tools.add_image import add_images_to_excel from tools.captcha_solver import crack_captcha page = ChromiumPage() for i in range(1, 8): page.get(f'https://bj.ke.com/ershoufang/pg{i}/') crack_captcha(page) # 人机验证按类型分流 page.wait(2) all_data = [] # ← 故障 2：写在了循环里 # 滚到底：比较滚动前后的纵向位置，位置不变才说明到底 for _ in range(30): height = page.rect.scroll_position[1] page.scroll.down(500) time.sleep(0.3) # 给图片留加载时间 if height == page.rect.scroll_position[1]: break lis = page.eles('xpath://ul[@class="sellListContent"]/li[@class="clear"]') for li in lis: info = { "标题": li.ele('xpath:.//div[@class="title"]/a').text, "总价": li.ele('xpath:.//div[@class="totalPrice totalPrice2"]/span').text, "图片网址": li.ele('xpath:.//img[@class="lj-lazy"]').attr('src'), # ↑ 故障 1：src 是占位图，真地址在 data-original } all_data.append(info) page.quit() df = pandas.DataFrame(all_data) df.to_excel('终版交付.xlsx', index=False) add_images_to_excel('终版交付.xlsx', df['图片网址'], 'H')

两个点值得看：if height == page.rect.scroll_position[1]: break 是「滚到底」的判据， 不看次数看位置；字段全部从 li 用 .// 相对定位，这是不串行的关键。 标红的两行是后来才发现的 —— 代码跑完不报错，数据也能落表，但落下来的东西是错的。

这个项目教了我什么

不报错 ≠ 对

三个故障没有一个抛出异常。程序照常退出、照常生成 xlsx、照常有 30 行 —— 但图片是白点、 180 条数据是假的缺失。交付前必须去表里看一眼实际内容，不能只看「跑完了」。

字段要验值，不是验有无

取到值不等于取对值。图片那一列 30/30「取到了」，值却全是同一张占位图。 判据应该是这一列的值有没有出现过 30 次重合，而不是空不空。

交付物是设计出来的

动工前先问清四件事：要多少条、要不要图片、页面结构复不复杂、有没有反爬； 先把样例截图和列名发过去确认，再出全量 —— 返工成本不该全落在自己身上。

稳定性写在判据里

滚到底靠「位置不变」而不是 range(50)，验证码靠类型分流而不是单一滑块， 采完显式 page.quit() —— 这三处都不是功能，是稳定性。
