项目背景

起点是一个纯静态页面：数据以常量数组写在 JS 里，刷新即还原， 没有用户概念，也没有后端。真正要练的不是「写个 CRUD」，而是 原地改造的克制 —— 在已经跑通的界面上做增量， 而不是推倒重写。9 个业务列表（每日计划 / 待办 / 语录 / 运动 / 饮食 / 打卡 / 媒体 / 备忘 / 金句） 的字段定义、必填项、排序规则，全部收在一张注册表里描述。

技术要点

一个注册表撑起 9 个列表

新增一个列表只需加一条配置，五套 CRUD 接口一行都不用改。

多用户隔离在数据层

业务表统一继承带 user_id 的抽象基类，查询自动收敛到当前登录用户，不是靠接口层记得加条件。

排序交给数据库

每日计划把 "07:00 – 07:40" 的起始时间换算成「当天第几分钟」存成派生列，ORDER BY 直接排，不用把数据全查出来在 Python 里排。

密码只存哈希

to_dict() 是专门给前端的版本，注释写明「绝不含 password_hash」—— 序列化边界就是安全边界。

接口契约对齐前端

对外暴露的 id 一律 str() 一次。前端 id 来自 DOM 属性、天生是字符串，两边严格相等才匹配得上。

真部署，不只是本地跑通

已部署到 Ubuntu 云服务器：gunicorn 单进程 + systemd 常驻开机自启，含云安全组放行与完整排查记录。

一个注册表撑起 9 个业务列表

# app.py —— LIST_REGISTRY：字段类型、必填、默认值、排序集中描述 LIST_REGISTRY = { "plans": { "model": Plan, "title": "每日计划", "fields": {"time": "str", "task": "str", "tag": "str"}, "required": ["time", "task"], "defaults": {"tag": "未分类"}, # 需求第 9 条：每日计划按时间升序。start_minutes 是 time 的派生列， # 同类时间再按 id 升序，保证顺序稳定（不会每次刷新换个样）。 "order": ("start_minutes", "asc"), }, "todos": { "model": Todo, "title": "待办清单", "fields": {"text": "str", "done": "bool"}, "required": ["text"], "order": ("id", "desc"), }, # ... 其余 7 个同构 }

9 个列表共用同一套增删改查实现，差异全部由这张表描述 —— 这也是「原地改造」能成立的前提。

踩过的坑：id 为什么必须是字符串

# app.py —— 源码里的原始注释（节选） # ⚠️ 关于 to_dict() 里为什么写 str(self.id) —— 别改回 self.id # # 数据库主键是 Integer，直接输出会变成 JSON 数字（"id": 8）。 # 但前端 app.js 里所有 id 都是从 DOM 属性上读回来的： # # editing = { id: btn.dataset.id } // ← 一定是字符串 "8" # data[list].filter(x => x.id === id) // ← 严格相等，数字 8 永远匹配不上 # # 也就是说「字符串 id」才是前后端之间既有的约定。后端给数字，就会出现： # 点「编辑」没反应、点「删除」不进入确认态 —— 而且不报任何错，最难查。 def to_dict(self): return { "id": str(self.id), # ← 对外一律字符串 "time": self.time, "task": self.task, }

前端因此一行都不用改。注意：只影响「发出去给浏览器」的数据，后端内部（路由 <int:item_id>、外键 user_id）走的仍然是整数。

部署与运行

  • 本地启动 — pip install -r requirements.txt 后 python app.py，首次启动自动建表。
  • 配密钥 — SECRET_KEY 必须设，否则拿到源码就能伪造登录态；FLASK_DEBUG 生产必须为 0。
  • 云服务器 — sync 代码 → 建 venv → 装依赖 → gunicorn 单进程启动。
  • systemd 常驻 — 写成服务单元，开机自启，进程挂了自动拉起。
  • 云安全组放行 — 这一步在服务器里改不了，必须去云控制台放行端口。
# ⚠️ 建表是「模块级」执行的，所以部署时必须单进程 gunicorn -w 1 -b 0.0.0.0:5000 app:app # 多 worker 会并发建表撞车 → sqlite3.OperationalError: table already exists # SQLite 本身是库级写锁，单进程也更合适
