个人管理台后端

这套东西原来是一个纯静态页：数据以常量数组写在 JS 里，刷新就还原， 没有用户，也没有后端。我用 Flask + SQLite 把它改成了能落盘、能登录、多用户互相隔离的应用。 真正的难点不是写接口，是九个列表的增删改查长得一模一样—— 我不想复制九遍，所以先写了一张注册表。

我为什么要动它

刷新一次，全没了

原型的数据写死在 JS 常量数组里。我改完一条计划，按 F5，它回到原样—— 那时候我就知道这东西只能看，不能用。

没有「谁的数据」这回事

静态页里所有人看到的是同一份。真要用起来，第一件事就得能分清 这是我的记录，不是别人的。

我不想复制九遍

九个列表的增删改查长得几乎一样。照抄九遍能跑，但改一个字段要动九处， 改漏一处就是隐藏 bug。

一张注册表，省掉四十五个接口

我先想清楚九个列表到底差在哪：字段名、哪些必填、默认值、按什么排序。 把这四件事描述出来，剩下的增删改查就是同一套代码跑九遍。

# 每个列表只描述「差异」，不写实现 LIST_REGISTRY = { "plans": { "model": Plan, # 对应哪张表 "title": "每日计划", "fields": {"time": "str", "task": "str", "tag": "str"}, "required": ["time", "task"], # 少一个就报错 "defaults": {"tag": "未分类"}, # 没传就用它 "order": ("start_minutes", "asc"), # 按时间升序 }, "checkins": { "fields": {"text": "str"}, # at 不在白名单里 "create_defaults": {"at": datetime.now}, # 时间由服务端盖章 }, # …… 其余七个同构，一共九条 }

新增一个列表 = 加一条配置。@app.route 那五套 CRUD 一行都不用改。

我是怎么串起来的

  • 先把原型的数据接住。原来的 HTML、CSS、JS 交互我一个都没重写， 只把「读常量数组」换成「打接口」。所以视觉和交互跟原型一模一样，换掉的只是底下那层。
  • 再给每条记录绑上 user_id。每张业务表都带一个指向 users 的外键， 查询时统一带上当前登录用户。别人的记录在我这里直接是 404，不是「没权限」。
  • 然后写一套通用 CRUD。五个路由吃 <list_name>， 去注册表里查这张表的规格，校验、填默认值、按配置排序，最后统一返回。
  • 写操作直接回全量。新增、修改、删除之后，响应里带的是最新的整页数据（boot）， 前端不用再补一次请求。这是我踩了坑之后才改的。
  • 最后补一套自测。test_api.py 只用标准库， 70 项覆盖登录态、五套 CRUD、排序、默认值、多用户隔离。

关键代码

五个路由共用一个入口函数，靠注册表分流 —— 这是整个后端最省事的地方：

# 从注册表取出这张表的「规格」 spec = LIST_REGISTRY.get(list_name) if not spec: return _fail("没有这个列表", 404) # 必填校验：报错要说人话，不是 missing field: time missing = [FIELD_LABEL.get(f, f) for f in spec["required"] if not payload.get(f)] if missing: return _fail("请先填写：" + "、".join(missing)) # 只收白名单里的字段，其余一律忽略 for name, kind in spec["fields"].items(): if name not in payload: continue value = _coerce(payload[name], kind) # "12" → 12 setattr(item, name, value) # 排序也读注册表：("start_minutes", "asc") order_field, order_dir = spec["order"] query = query.order_by(getattr(model, order_field).asc() if order_dir == "asc" else getattr(model, order_field).desc())

我踩过的坑

  • 打卡时间不能让前端传。我第一版把 at 也放进了白名单， 结果前端能随便填一个昨天的时间，「今天打卡了没」就废了。 后来把它挪出 field 白名单，改成 create_defaults 由服务端盖章。
  • 多进程部署会撞车。建表是模块级执行的，gunicorn -w 4 会让四个进程 同时建表，报 table already exists。只能单进程跑 —— SQLite 本身也是库级写锁， 单进程更合适。
  • 写操作只回一个 ok，前端要自己再拉一遍。一开始就这么写的， 每改一条数据要发两次请求，列表还得自己合并。后来改成直接返回最新的整页数据， 前端拿到就是最终状态，少一次往返也少一堆状态同步的 bug。
  • 别人的记录该是 404，不是 403。先说「无权限」等于承认这条记录存在。 统一查 user_id，查不到就是 404，连存在性都不暴露。

怎么运行

# 1. 装依赖 pip install -r requirements.txt # 2. 起服务（首次启动会自动建表 + 灌演示数据） python app.py # 默认 127.0.0.1:5000 PORT=5111 python app.py # 换端口 # 3. 跑自测（70 项，只用标准库） python test_api.py
