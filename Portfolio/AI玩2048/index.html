这个项目我想要的不是「让 AI 聊 2048」，是让它自己玩： 截图当前棋盘 → 模型看完回答一个方向 → 程序替你按方向键 → 再截下一张。 一圈一圈转下去，中间没有我插手。下面这盘棋你可以自己下，也可以让 AI 接手， 它每走一步的想法都摊在旁边。

原来的版本是这么转的：一圈三步，没有人在里面 对应 AI玩2048.py 里的三段
STEP 1 · 感知

截游戏画面

DrissionPage 打开 4399 那个 2048，iframe.get_screenshot() 只截游戏区，不截整个网页。

STEP 2 · 决策

让模型看图选方向

截图转 base64 塞进 image_url，模型回一个单词。 提示词里明写「不要包含其他文字」。

STEP 3 · 执行

真的按下去

先点 div.container 拿到焦点，再发方向键。 不点这一下，键是发不进 iframe 的。

我为什么要绕这么一大圈

读棋盘比玩游戏难

2048 的格子没有 id、没有 data 属性，是一层层 div 画出来的。 与其去解析 DOM，不如直接让模型看图——人怎么玩，它就怎么看。

这一步跨过去就是 Agent

截图、判断、动手，再回头看结果。三步接成环，中间没有人， 这就是它和「问一句答一句」最大的区别。

它得自己发现错

方向键按下去可能什么都没变（那个方向走不动）。程序不看返回值， 下一张截图会告诉它——决策错了，画面会自己纠正。

闭环是怎么转的

  • 先只截游戏区。整个网页截图会把广告、按钮全带上，模型会被干扰。 iframe[@id='flash22'] 单独截，画面里只有棋盘。
  • 图片要转成 base64。本地文件不能直接给模型，得先读二进制、 再 b64encode、拼成 data:image/png;base64,... 这种格式。
  • 提示词只让它回一个词。「先确认每个数字的位置，优先选能合并的方向」是思考引导， 「只回答 up、down、left、right」是输出约束。两句都要有。
  • 返回值要容错。模型有时会写成 **left** 或者 「我选 left」。所以判断用的是 if "left" in a，不是 ==。
  • 按键之前必须先点一下容器。iframe 里的键盘事件要有焦点， 不点 div.container 的话方向键发不进去，看起来就是「程序在跑但棋盘不动」。
  • 然后立刻截下一张。不判断这一步有没有变化， 下一圈的截图自然会反映真实局面——这比程序自己猜要可靠。

关键代码

感知那一段，只截 iframe 是刻意的：

# ① 感知：只截游戏区，别把广告带进去 iframe = page.ele("xpath://iframe[@id='flash22']") iframe.get_screenshot("2048.png") # ② 决策：图片转 base64，塞进多模态输入 with open("2048.png", "rb") as f: img_data = base64.b64encode(f.read()).decode("utf-8") result = f"data:image/png;base64,{img_data}" response = client.chat.completions.create( model="glm-5.3-flash", messages=[ {"role": "user", "content": [ {"type": "text", "text": prompt}, {"type": "image_url", "image_url": {"url": result}} ]} ] ) # 模型可能回 "**left**" 或 "我选 left"，所以用 in 判断 a = response.choices[0].message.content ans = "" for d in ("left", "right", "up", "down"): if d in a: ans = d break # ③ 执行：先点容器拿焦点，再发方向键 container = iframe.ele("xpath://div[@class='container']") container.click() container.input({"left": Keys.LEFT, "right": Keys.RIGHT, "up": Keys.UP, "down": Keys.DOWN}[ans])

这一页里的 AI 和原来不一样，我说清楚

原来：模型看图判断

截图 → 多模态模型（智谱 GLM）看图 → 回一个方向。优点是不需要懂 2048 规则， 人怎么玩它就怎么看；代价是每走一步都要等一次网络请求，而且模型偶尔会看错格子。

这一页：策略算法判断

上面那个棋盘用的是 Expectimax + 启发式评估：把四个方向都往后算几步， 把随机冒出的 2/4 一起算进期望值，再比哪个方向期望分最高。 为什么换：浏览器里没有你的智谱 Key，我不能调多模态模型。 与其假装，不如把另一条路做出来——而且这条路能下得更好，也更快。

两条路的共同点是：都把「感知 → 决策 → 执行」拆开， 每一步单独可观察。区别只在第二步用什么在判断。

我踩过的坑

  • 方向键发进去了，棋盘没动。第一次跑，程序日志一直正常输出方向， 但截图里格子一点没变。原因是没有先 container.click() 拿焦点—— 键盘事件需要一个能接住它的元素。
  • 整页截图模型根本看不清。一开始截整页，广告和按钮占了三分之二， 模型经常答一个和棋盘无关的方向。改成只截 iframe 才稳定。
  • 模型不太老实，会加解释。提示词里已经写了「不要包含其他文字」， 它还是偶尔回一句「我选择向左移动」。所以判断必须用 in，不能 ==。
  • 一步一请求，很慢也很贵。这个循环每转一圈就是一次带图的请求， 几十步下来开销不小。这也是我后来去做策略算法的原因—— 能本地算的，就别每次都问模型。
