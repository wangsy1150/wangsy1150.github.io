工具打包集

自己写的脚本，发给不会装环境的人就是一堆 .py。打包成 exe 才算交到别人手里。 我按四种情况各打了一遍：同一条 --onefile，最小的 7.0MB，最大的 203.0MB —— 差 29 倍。 下面这九根柱子是我机器上真实的产物体积，一个字节都没编。

为什么柱子差这么远？因为 PyInstaller 的 onefile 不是"压缩我的代码"， 而是把整个 Python 运行时 + 用到的每一个库都塞进一个 exe。 你 import 了 random，就只塞 random；你 import 了 pandas，就得把 numpy、pytz、sqlalchemy 那一串全带上。 所以体积不是你写了多少行，是你 import 了什么。

最要命的一步：打包之后图片去哪了

开发时 cat_normal.png 和脚本在同一个文件夹，open("cat_normal.png") 就能读到。 但 onefile 的 exe 双击之后，会先把自己解压到一个临时目录再运行 —— 当前目录已经不是脚本所在的目录了， 相对路径全部失效，图片裂开、图标变白框。

四种情况，各自卡在哪

① 单文件：最省事

没有资源、没有第三方库，--onefile 一句话就完了。三个 exe 都在 7–10MB，因为 tkinter 和 random 就这么多。

② 静态资源：路径要重写

图片得用 --add-data 带进去，代码里还要用 sys._MEIPASS 改路径。两件事少一件，图就裂。

③ 第三方库：体积失控

pandas 默认打不全，要 --collect-all；一加就 203MB。同样的程序只 import requests 时是 16MB。

我踩过的坑

1

--add-data 的分隔符：Windows 是 ;，macOS/Linux 是 :

我写的 --add-data "yzm.png;." 在 Windows 上没问题，换台 Mac 打包就报错 —— 因为 ; 在那边是路径的一部分。 同一条命令不是跨平台的，这一点最容易在"我给你发个命令你照着敲"的时候翻车。

2

--windowed 之后，报错全都不见了

加 --windowed（spec 里是 console=False）exe 双击不再弹黑框，很好看 —— 但程序一崩，什么提示都没有，窗口直接消失。

我现在的顺序是：先带控制台打包跑通，确认没异常，最后才加 --windowed 再打一次。反过来做，等于自己把唯一的出错信息关掉了。

3

--collect-all pandas 换来 203MB

pandas 的好处是它会把 pandas 的所有子模块、数据、二进制一次性收进来，打包成功率高； 坏处是它连测试数据、所有可选依赖一起收 —— demo02 就这么变成了 203.0MB，而同样只打印一句话的 requests 版本是 16.0MB。

这不是"必须接受的代价"：正确的做法是 --exclude-module 排掉用不到的（matplotlib / tests / IPython），或者干脆用 onedir 模式，第一次启动还更快。

4

控制台程序一秒闪退

双击 exe，黑框一闪就没了 —— 因为程序跑完就结束了，打印的内容根本来不及看。 我在 main.py 的最后加了一句 input("按回车键退出...")，就为了让它停住。

这是最土也最有效的办法；正经做法是写日志文件，但当时我只需要看见它跑完了没。

有一件事我没跑完，如实说：目录里还有一个 demo03.py（pandas 读数据、再 to_csv 写出 一个文件）， 但它没有对应的 exe —— dist 里只有 demo1 和 demo02。 为什么没打，我没有当时的记录，不能替自己编一个理由；只能说这个场景我停在源码，没交产物。 要补的话，它其实是个好问题：onefile 下程序往磁盘写东西，到底该写在哪、下次启动还在不在。

边界：哪些是我做的

这九个 exe 是 9 月 30 日晚上打出来的，PyInstaller 的命令和 spec 写法是照官方文档学的，不是我摸索出来的。
属于我的是：① 这九个体积数字（ls -l 实测）和"29 倍"这个对比； ② 上面四个坑里，第 1、2、4 条是我自己撞过的，第 3 条是看着 203MB 去查为什么才知道的； ③ 这一页的条形图、命令生成器、路径对照，是我为了把这些事讲清楚自己写的。
还有一句实话：打包集本身不算一个"项目"，它是同一天晚上练的四套动作。 它的价值不在代码量，在于我现在知道"发给别人能跑"和"在我机器上能跑"之间隔着什么。
