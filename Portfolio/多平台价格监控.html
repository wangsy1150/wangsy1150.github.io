刚才那次实抓，翻车翻在哪

1

京东第 1 个链接：元素没找到

脚本还在，sku-title-name 和 product-price--value 这两个 class 却找不到元素了。 同一份代码、三个链接只有它翻车 —— 大概率是这类商品页走了另一套模板。 我不确定具体原因，下次带上登录态跑一遍才能下结论。

2

淘宝：抓回来一个「起」字

淘宝价格选择器 xpath://div[@class="block2--MLcO9YdF"]//span[last()] 取最后一个 span， 结果取到了价格后面的「起」字 —— 数字就在它前一个。 float("起") 会直接抛异常，真实脚本里这一条会崩，而不是悄悄给错数。 这也是为什么要 try 住每一条，单条翻车不能拖死整轮。

3

淘宝第 1 个链接：整页都要登录

标题和价格全找不到 —— 无登录态的会话被淘宝挡在了页面外。 这就是为什么真实脚本里淘宝那条路要靠 cookie 登录态，凭据从环境变量读，不落代码。

它到底怎么跑的

# 监控京东商品价格.py —— 核心就这一段（真实仓库里的代码） from DrissionPage import ChromiumPage from serverchan_sdk import sc_send ideal_price = 4500 # 心理价位 product_urls = ["https://item.jd.com/100359969926.html", ...] page = ChromiumPage() for p_url in product_urls: page.get(p_url) title = page.ele('xpath://span[@class="sku-title-name"]').text[:10] price = page.ele('xpath://span[@class="product-price--value"]').text if float(price) < ideal_price: sc_send(SENDKEY, # 命中 → 微信推送（SendKey 从环境变量读） f"你关注的{title}已降价", f"点击立即购买{p_url}") page.wait(5) # 防反爬，隔几秒再走下一个

技术要点

多平台适配

京东、淘宝/天猫各一份采集脚本，共用同一套「抓价 → 比对 → 推送」主流程，选择器按平台各自维护。

定时调度

APScheduler 管理定时任务，按设定间隔自动执行；独立脚本负责启动与结束，进程不长期驻留。

微信推送

接入 Server酱，把「你关注的 xx 已降价」推到微信；SendKey 走环境变量，不写进代码。

失败不装看不见

这次实抓 6 条里翻车 3 条，翻车原因分析就摆在本页 —— 监控脚本的价值在真实可用，不在演示好看。

执行流程

  • 加载目标 — 读取商品链接列表和心理价位（脚本里的真实配置：京东 4500 / 淘宝 4000）。
  • 逐个抓价 — 浏览器打开商品页，按平台选择器取标题与价格。
  • 比对阈值 — 价格低于心理价位才进入提醒分支，否则只记录不打扰。
  • 推送通知 — 通过 Server酱把商品名和购买链接推到微信。
  • 定时收尾 — 由调度脚本启动与结束，全程无人值守。
说明：监控类脚本的价值在「无人值守」——它不解决「买不买」，只解决「什么时候该看一眼」。 商城页面天天改版，选择器就是会失效，所以每个平台的解析逻辑各自隔离，某一站改版不会拖死整条链路 —— 上面那 3 条翻车记录就是这句话的现场证据。
